这是一份关于编写任何供代理使用的文档的参考：skill、`AGENTS.md` / `CLAUDE.md`，或通过指针访问的文档。这些文档的形式不同，但写作原则相通：用清楚的指令让代理每次遵循一致的_流程_，不要求每次产出相同的结果。

当你编写的文档是 skill 时，阅读 [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md)，了解 frontmatter、调用方式选择和路由型 skills。

## 上下文指针

**上下文指针**是代理上下文中的一条引用：它指向上下文之外的某份材料，并说明何时需要读取它。skill 的 description 就是一种上下文指针；`AGENTS.md` 中指向某份文档的一行文字也是同一种对象。决定代理何时访问材料、以及访问有多可靠的，是指针的_措辞_，而不是它指向的目标。如果读取必要材料的条件写得含糊，代理就可能漏读：先把指针写明确；仍然无效时，再把材料直接写入当前文档。

指针承担两项工作——说明材料是什么，并列出应触发访问的**分支**（分支是文档所处理的一种独立情形，因此不同运行会沿不同路径穿过文档）。始终加载的指针中，每个词都会在每轮对话消耗成本，因此应比正文更加精简：

- **将引导词放在最前面**——让代理尽早识别触发条件。
- **每个分支只设一个触发条件。** 仅仅给同一分支换名的同义词，只是把一个分支写了两遍；合并它们，只保留真正不同的分支。
- **删除正文已经说明的职责或定位。**

## 两类负载

你添加的每份文档和每个指针，都会消耗以下两种预算之一：

- **上下文负载**——始终加载的材料占用代理上下文窗口的成本：`AGENTS.md` 中的一行、skill description，以及每轮对话中无论是否触发都会留在上下文并消耗 token 与注意力的所有内容。
- **认知负载**——人需要承担的成本：有哪些文档，以及何时应访问每份文档。人就是索引。它并非需要最小化的成本——而是人类自主权的代价；把它花在人类判断真正重要之处，在不需要人类判断之处将其移除。

按需读取的材料只需让指针常驻上下文，无需一直加载全文。完全没有指针的材料，则需要用户自己记住何时使用。

## 信息层级

文档由两类内容构成——**步骤**（代理按顺序执行的动作）和**参考信息**（按需查阅的定义、规则与事实）——两者可以自由组合：全是步骤（操作流程）、全是参考信息（评审规则、本 skill），或两者兼有。核心决策是把每项内容放在**信息层级**的哪一层；这是一架按代理对材料的即时需要程度排列的梯子：

1. **文件内步骤**——主要层级：代理要按顺序做什么。
2. **文件内参考信息**——按需查阅。它们往往是一组并列内容（例如评审的每条规则都位于同一层）——这种安排合理，不必刻意拆分。
3. **披露式参考信息**——移到单独文件中，借助上下文指针访问，只在指针触发时加载。其范围可以从同一文件夹中的相邻文件，一直延伸到存放于任意位置、可由任何文档指向的完全外部参考资料。

下移得太少，顶层就会臃肿；下移得太多，又会隐藏代理真正需要的材料。关键是找到两者之间的平衡。

**渐进式披露**是沿梯子向下移动——把内容移出主文件并放到指针之后——从而让顶层保持清晰易读。它首先不是一种 token 优化，而是让文档层次保持清楚的方法。按使用场景判断最直接：内联每条分支都需要的内容，只把部分分支才会访问的内容放到指针之后。对于包含步骤的文档，本应移到独立文件的参考信息若留在正文中，会淹没操作步骤，让代理容易漏读，影响执行的稳定性和文档的可读性。

**共置**是文件内部的配套原则：层级决定一项内容要下移_多远_，共置则决定内容到达某处后_与什么相邻_。将同一概念的定义、规则和注意事项放在同一标题下，而不是四处分散；这样读到其中一部分时，也能一并了解相关内容。判断标准是：文档读起来应像专门为代理编写的文档——相关材料归组后便有这种感觉，四散时则没有。（这不同于重复：重复是在两处表达同一含义；散布则是把一个含义拆散到多处。）

**蔓延**是这里的失败模式：文档单纯过长，即使每一行都仍然有效且独一无二。过量内容会稀释注意力，每增加一行，也就多了一行需要持续保持相关。解决办法仍是这架梯子：把参考信息放到指针后披露，并按分支或顺序拆分，让每条路径只携带它真正需要的内容。

## 步骤与完成标准

每个步骤都以一项**完成标准**结束——即告诉代理工作何时完成的条件。两种属性使它成为有效控制手段：

- **清晰度**——代理能否分辨已完成与未完成？模糊的边界（“已经理解”）会诱发**过早完成**：步骤尚未真正完成便结束它，注意力滑向_赶紧完成_。已经呈现出来的后续步骤（**完成后步骤**）会诱使代理急着往下做；清晰的完成标准能约束这种倾向。按此顺序防御：**先收紧边界**（局部且成本低）；只有当边界本质上无法清晰，_并且_你确实观察到抢跑时，才通过拆分流程隐藏后续步骤——而隐藏只有跨越真正的上下文边界（交接或派遣子代理）才有效；内联调用会让后续步骤继续留在上下文中，什么也没有清除。
- **要求强度**——标准要求做到什么程度。“每个修改过的模型都已涵盖”会迫使代理进行全面工作，而“生成变更列表”不会。要求强度推动**深入检查**——代理在执行任务时深入调查、核实的工作，它隐含在措辞中，而不是另写成一个步骤——且不受步骤边界限制：“应用每条规则”能够约束一组并列的参考信息，就像“完成每个步骤”能够约束一段流程一样；因此，即使一份文档全部由参考信息构成，也仍能设定穷尽性门槛。

有效的完成标准既能验证，也能确保该做的工作没有遗漏。

## 何时拆分

把一份文档拆成两份，会消耗两类负载中的一种，因此只有拆分确有收益时才这样做：

- **按顺序拆分**——当完成后步骤会诱使代理草率处理眼前步骤时，拆分一段连续步骤。让后续步骤保持不可见，能促使代理在当前任务中做更充分的检查。也要警惕反向影响：合并流程会让每个步骤看见随后的一切，从而诱发过早完成。
- **按调用方式拆分**——这是 skill 特有的情况：参阅 [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md)。

## 引导词

**引导词**是一个已存在于模型预训练中的紧凑概念，代理在执行文档时会用它思考（例如 _lesson_、_fog of war_、_tracer bullets_）。将它作为 token 反复使用，而不要把整句话反复写出；这个词在不同位置的用法会共同说明其含义，并借助模型已有的知识，用较少的 token 引导一整套行为。自造词也可以使用，但必须定义清楚；模型不熟悉这些词，需要花更多篇幅解释。因此，优先选用已有词。

引导词分别影响执行和调用。在正文中，它引导_执行_：每当这个词出现，代理都会调用同一种行为；在并列的参考信息中，它还会把注意力集中到需要寻找的一类事物上。在指针中，它引导_调用_：当同一个词同时存在于提示词、文档和代码库中时，代理会把这种共享语言与材料关联起来，从而更可靠地访问材料。

主动寻找使用引导词重构的机会。同一组概念在多处反复解释，或一句长话仍说不清一个想法时，可以尝试用一个简洁的术语来概括：

- “快速、确定、低开销” → _tight_（一个 _tight_ 循环）。
- “一个你相信的循环” → _red_——模糊的门槛变成二元、可观察状态（循环会因 bug 变成 _red_，或者不会）。

这样既能节省 token，也能用明确的概念帮助代理组织思路。逐份检查文档，找出可以用引导词替代的重复解释。

**否定式指令**是紧邻这一控制手段的失败模式：通过禁止某种行为来引导，会把被禁止的行为带入上下文，反而使其更容易发生。_不要想大象_，结果满脑子只剩大象；否定词只是一个弱修饰语，压不过被强烈激活的概念，于是禁令读起来一半像是在要求做那件事。提示**正向目标**——直接说明目标行为（“写单行注释”），让被禁止的行为根本不出现。只有当某项硬性护栏无法用正向方式表述时，禁止语句才值得保留；即便如此，也要把它与正向目标配对，让注意力落在该做什么上。

## 删减

- 让每个含义都只有一个**单一事实来源**：一个权威位置，使行为变更只需编辑一处。**重复**——同一含义出现在多个位置——会增加维护和 token 成本，并把某个含义在层级中的显著程度抬高到超过其真实级别。（这恰好是引导词的意外反面：引导词有意重复 token，却从不重复含义。）
- **环境**本身也是事实来源——`package.json` 脚本、配置文件、目录布局、`--help` 输出——而重复描述这些内容的文档就是一份**缓存**：它复制了查询结果，只有在查询昂贵时，其负载才有价值。只缓存代理无法通过查看环境发现的内容：未成文的约定、某项选择背后的原因、任何配置都不会透露的陷阱。将单文件、单命令即可完成的查询留给环境，以便每次都能读取当前状态。
- 检查每一行的**相关性**：它是否仍与文档的职责有关？一行内容可能因为从未影响任务（纯粹说明，或本应披露出去的分支），或因其描述的行为与世界发生变化而失去相关性。较短的文档更容易保持相关。如果不定期删减，默认结局就是**沉积**：过时内容层层堆积，因为添加让人安心、删除令人不安，直到你不得不翻过层层旧内容，才能找到仍然有效的指令。
- 逐句寻找**无效指令**：模型本来就会默认遵循的指令，花费了负载却没有产生任何作用。判断标准——相较默认行为，它是否改变了行为？——取决于模型，而非读者：两个人对一条指令是否无效存在分歧，本质是在争论默认行为；应通过实际运行文档解决，而不是辩论。如果一个句子未通过测试，就删掉整个句子，不要只修剪几个词。这个测试同样适用于引导词：弱到无法超越默认行为的词（代理本来就算比较仔细时还说 _be thorough_）也是无效指令；修复方式是换成更强的词（_relentless_），而不是换一种技术。
