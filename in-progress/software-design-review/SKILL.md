# 软件设计哲学审查

审查的目标不是寻找“看起来不够优雅”的代码，而是找出这次变更是否让系统更难理解、更难修改，或把复杂性转嫁给调用者和未来的维护者。

## 核心判据

把下面这句话当作总原则：

> 如果一个变更使未来的读者无法在局部理解它，或使一个小需求必须在多个地方同步修改，它就可能增加了系统复杂度。

书中的复杂性不是代码行数，而是理解和修改系统所需的工作。重点观察三种症状：

- **Change amplification（变更放大）**：一个概念或需求的改变会牵动许多不应牵动的文件、调用方或层。
- **Cognitive load（认知负荷）**：调用者必须学习额外的参数、顺序、格式、异常、配置或隐藏副作用。
- **Unknown unknowns（未知的未知）**：不清楚还要改哪里、还要知道什么，或无法判断改动是否完整。

复杂度通常来自两类根因：**dependency（依赖）**和 **obscurity（模糊）**。以读者和未来修改者的视角评审，而不是以作者已经知道实现细节为依据。

## 范围与边界

- 主要审查 MR/PR 改动的新增或修改代码；只向周围代码扩展到足以确认职责、调用关系和影响面。
- 先读取 MR 描述、关联 issue/spec、仓库的 `AGENTS.md`、贡献指南、编码规范和相关 ADR。仓库已有的明确约定优先于本 skill 的启发式判断。
- 本 skill 可以指出设计会如何影响正确性、测试性、性能或安全性，但不把这些专项审查冒充成已完成的结论。
- 不因代码长、类多、缺少某个设计模式或实现内部复杂就自动报问题。深模块的实现可以复杂；关键是它是否用足够简单的 interface 隐藏了复杂性。
- 不修改工作树，不替用户发布 MR 评论，不把“可以更漂亮”写成缺陷。除非用户另行授权，只读地检查和验证。

## 审查流程

### 1. 锁定准确的 MR diff

先确定一次且只确定一组比较范围：

1. 若用户给出 MR/PR URL 或编号，读取其 target/source 分支及 pinned base/head SHA。优先以这对 SHA 重建 diff；若平台只提供移动的分支名，则在同一时刻将它们解析为 `base_sha`/`head_sha` 并记录这是本地快照。平台渲染的 MR diff 只作交叉核对，若两者不同，报告 scope limitation。
2. 若用户明确给出 base 和 head，先解析并保存为不可变的 `base_sha` 与 `head_sha`（例如 `git rev-parse --verify '<ref>^{commit}'`），后续 diff、log 和验证都只使用这两个 SHA。若只给一个 commit，先解析该 commit 及其选定的 parent SHA，可只审查该 commit 相对 parent 的范围（`<parent_sha>..<commit_sha>`），并记录这一约定；若该 commit 是 merge commit，先确认使用哪个 parent。若只给分支或 tag，只把它当作 head，必须取得明确的 base/target；不能用当前 `HEAD`、默认分支或任意历史深度代替。无法得到 base 时询问用户，不要猜测 `HEAD~N`。
3. 确认 ref 可以解析，并记录一条 canonical diff 命令，例如 `git diff <base_sha>...<head_sha>`（three-dot，以 merge-base 为基准）。同时记录 `git log <base_sha>..<head_sha> --oneline` 作为提交摘要；merge commit 下日志与 diff 不必一一对应。若在解析后发现远端/平台 ref 已指向不同 SHA，报告 scope mismatch，不要静默改审查范围。
4. 若 ref 无效、diff 为空，或本地代码与 MR SHA 不一致，先报告并停止设计判断。空 diff 不应写成“未发现违反项”，而应给出 `Design-philosophy recommendation: unable to review`。
5. 将工作树中未包含在该 diff 的本地修改视为无关内容，不把它们混入发现。

如果拿不到 MR 元数据但用户给出了可解析的 base/head refs，可以继续做基于该 diff 的设计审查，并在 Scope 中说明缺口；如果连可解析的 base/head 都没有，无法锁定变更，应报告 `unable to review`，而不是猜测比较范围。拿不到关联 spec 不妨碍设计轴审查，但必须说明无法据此判断需求是否满足。

### 2. 建立变更地图

从 diff 和必要的上下文中标出：

- 新增或改变的 public interface：方法、函数、构造器、类型、事件、配置、CLI 参数、数据库/网络协议和序列化格式；
- 每个改动模块的职责、调用者、被调用者，以及所在层级；
- 新增的异常、状态、特殊分支、默认值、可选参数和副作用；
- 受影响的测试、文档、迁移脚本和兼容性承诺。

先理解“谁需要知道什么、什么时候需要知道”，再判断是否有泄漏；不要只按文件名或目录名推断模块边界。

### 3. 逐项检查设计信号

对每一类信号都问：它在本次 diff 的哪一行出现？谁因此多承担了什么？一个具体的未来变更会怎样放大成本？证据不足时只在内部保留待核实项；只有有具体 diff 证据、明确影响或可回答问题的项才进入最终输出。

#### A. 模块深度与 interface

寻找：

- **浅模块（shallow module）**：interface 几乎和 implementation 一样复杂，或只增加了一层名字而没有隐藏重要行为；
- **Pass-through method/class**：只把同样的参数、异常和返回值转交给下一层；
- public interface 通过大量参数、选项、顺序要求、异常或副作用暴露内部决策（**overexposure**）；
- 为了“每个类/方法都很小”而拆分，结果读者必须在几个文件之间来回跳转；
- 常见路径必须手工组合多个对象或了解少见功能才能工作。

应用**删除测试（deletion test）**：假设删除该 wrapper 或中间层，复杂度是否会重新出现在每个调用方，还是只需把调用直接移到一个真正负责的模块？前一种通常说明该层正在集中复杂度、提供有效的 leverage；后一种才是浅层风险。

例如，删除只转发 `UserStore.save` 后，调用方只需直接调用已有的底层保存方法（如 `BlobStore.put`），这是浅层信号；删除真正封装版本、编码和迁移规则的 `ProfileStore` 后，每个调用方都得重新学习这些细节，则说明该模块在提供 leverage。

参数看起来完全透传也不等于必然浅：如果 wrapper 还拥有语义翻译、兼容性窗口、依赖反转、鉴权或指标契约，删除它会把这些知识散落给调用方；这类 adapter 可以保留，但应在 interface 或 MR 说明中显式写出它的责任。

不要仅凭长方法、较大的类或多个公共方法报告问题。若长实现内部协作紧密、调用者只需看见一个干净的 interface，它可能正是深模块。

#### B. 信息隐藏与层次

寻找：

- 同一个表示、协议、文件格式、业务规则或设计决策被复制到多个模块（**information leakage**）；
- 代码按“先读取、再修改、再写回”的时间顺序拆开，却让多个模块都知道同一格式（**temporal decomposition**）；
- 上层检查下层的内部字段、状态机、存储布局或错误细节，而不是通过抽象操作；
- 相邻层使用近似的抽象，出现重复 interface、装饰器堆叠或 pass-through variable；
- 一个 context/参数对象变成无约束的变量垃圾袋，让不需要它的中间方法也被迫知晓它；
- interface 文档必须解释实现步骤，才能让调用者正确使用。

好的分层应让每层有不同的抽象，并让每个易变的设计决策尽量只由一个模块拥有。相同的公共 wire format 在专门的 parser/serializer 中重复出现，若所有权、兼容性和测试边界明确，可能是有意的；只有内部表示或易变决策被多个模块各自解释时才算信息泄漏。信息需要对调用者可见时不要强行隐藏；目标是减少不必要的可见信息，而不是追求绝对封装。

#### C. 一般性、特殊性与组合

寻找：

- **Speculative generality（投机性通用）**：MR 为尚未出现的需求加入未使用的 hook、泛型层、参数、策略或配置；
- 通用机制混入某个特定业务场景，导致两者未来必须一起改（special-general mixture）；
- 为一个很小的功能新增 decorator、adapter、base class 或 feature flag，而直接放入现有模块会更简单；
- 重复代码暗示缺少合适抽象，但抽象本身的 interface 成本却没有被比较；
- 继承让子类依赖父类实现细节、继承了大部分不用的行为，组合可能更清楚。

通用性的合适尺度是：功能满足当前需求，interface 足够通用但仍然易用。问“覆盖当前需求的最简单 interface 是什么”“这个方法会在多少种场景使用”“当前调用者是否真的更容易使用”。不要因为未来“也许会用”就要求抽象。

#### D. 放置复杂性、错误与特殊情况

寻找：

- 底层模块把本可统一处理的例外、重试、默认值或边界情况推给每个调用者；
- API 增加一个参数只是把开发者尚未解决的设计决定转嫁给用户；
- 常见路径被迫处理罕见功能、异常或配置；
- 同一个特殊情况在多层重复判断，而不是让正常设计自然覆盖它（**define errors/special cases out of existence**）；
- 异常、错误码或恢复协议穿过许多层，扩大了 interface 的知识范围。

“让模块开发者多承担一点、让使用者少承担一点”是方向，不是绝对规则。若调用者确实拥有该选择的信息，暴露配置或错误是合理的；若错误不可恢复、发生极少且继续处理会更复杂，崩溃也可能是有意设计。评审要说明具体的责任归属，而不是笼统要求“内部处理一切”。

#### E. 聚合、拆分与耦合

寻找：

- 两段代码共享关键知识、总是一起使用，或互相无法独立理解，却被拆到不同模块，造成重复和来回跳转；
- 不相关的逻辑被塞在同一模块，导致它因多个互不相关的原因变化（divergent change）；
- 一个逻辑变更分散到许多文件（shotgun surgery/change amplification）；
- 两个方法有大量隐式顺序、共享状态或互相依赖，单独阅读不了（conjoined methods）；
- 拆分唯一理由是行数或“一个方法只能 N 行”。

应根据共享信息、双向共同使用、概念重叠和独立可理解性决定合并或拆分。组件越多并不自动越好：每个新 interface、参数、类和定义都会增加读者必须学习的基础设施。

#### F. 演化、文档、命名与显然性

寻找：

- MR 以最小补丁、复制分支或额外 flag 绕过了一个已经暴露出来的职责问题，且有可信的后续变更会继续放大它（tactical programming）；
- 改变了 interface、约束、不变量、错误行为或副作用，却没有在临近代码处更新 interface 文档和测试；
- 注释只重复代码，或把另一模块的实现决策复制到调用处；
- 缺少描述“做什么、返回什么、前置条件、顺序、异常和副作用”的必要 interface 文档；
- 名称含义过宽、不一致或无法在脱离实现时形成准确图像；
- 相似的事情没有遵循同一约定，或为了表面一致性把本质不同的行为强行套进同一模式；
- 代码行为违反读者对约定、默认值、退出状态或错误路径的预期。

代码审查本身是“显然性”测试：如果经过足够上下文仍无法从外部声明理解行为，先把困惑定位为缺失抽象、命名或文档问题，再决定哪种修复最小。不要要求每个简单函数都加注释。

#### G. 测试、继承与性能声明

只在与本次设计变化相关时检查：

- public interface 或关键不变量改变，却没有能跨越该 interface 的测试，使重构和回归无法安全进行；
- 继承层级泄漏父类状态，或子类拒绝大部分继承契约；
- MR 声称性能提升，却没有 baseline、测量方法、代表性输入或回归保护；
- 为性能增加了可见的复杂 interface，却没有证明收益；如果复杂性被可靠地藏在 implementation 内且收益已测量，通常不应阻塞。

单元测试的价值是给结构性变化提供安全网，不是以测试数量衡量设计质量。性能直觉不可靠，先测量再优化；简单设计通常已经足够快。

### 4. 验证每个候选发现

每个准备报告的发现都必须经过以下检查：

1. 回到 diff 的具体 hunk，引用新代码中的文件和行号；必要时再读调用点、接口声明、测试和配置。
2. 写出被违反的原则（例如浅模块、信息泄漏、变更放大），以及新增的认知负荷或依赖。
3. 构造一个合理而具体的后续变化，说明它会牵动哪些地方；不要只说“以后可能难维护”。
4. 对 public interface 或模块拆分执行一次 **Design it twice**：至少想出一个更简单或不同的替代方向，比较两者的 interface 成本、通用性和实现收益，并说明各自隐藏了什么、把责任放在哪里。不要在没有上下文时要求完整重写。
5. 检查 MR 描述、ADR 或现有标准是否明确解释了这个取舍。若是有意且合理的取舍，降为 trade-off 或不报告。
6. 运行与问题相关的最小验证（例如目标测试、类型检查、静态搜索或基准）；记录命令和结果。优先在临时 worktree/独立 checkout 或容器中验证，例如用 `git worktree add --detach <temporary-path> <head-sha>`；完成后只移除自己创建的临时 worktree。若必须在当前 checkout 运行，先确认整个 worktree 的 `git status --short` 为空；只要存在任何用户已有修改或未跟踪文件，就改用隔离 checkout，不能只凭“相关文件看起来干净”判断。把缓存和生成物导向临时目录（例如 Python 设置 `PYTHONDONTWRITEBYTECODE=1`、pytest 使用临时 cache），并确认没有碰到用户已有修改。无法验证时明确标注缺口。

把发现分成四种状态：

- **Violation**：diff 和上下文已经足以证明设计违反原则；
- **Risk**：diff 有具体迹象和合理后果，但尚缺调用关系、需求或运行证据；输出一个可回答的问题和补证据路径，不把未证实的可能性当成结论；
- **Question**：需要作者澄清一个设计意图或责任归属，但目前没有主张它一定有害；
- **Trade-off**：确实增加复杂性，但有明确收益、范围受控且接口影响可接受；记录理由，不当作缺陷。

Trade-off 只有在 MR/spec/ADR、测量结果或兼容性计划中有证据说明收益，并且有明确 owner、范围或退出条件时才成立；只有作者口头说“以后有用”时，标为 Risk。兼容 wrapper 若没有迁移/弃用边界，也不要自动视为合理取舍。

同一个根因只报告一次，后果写在同一项中。Risk 也必须有具体 diff 证据和一个可回答的问题，不能把纯粹的未来想象列成发现。不要把预先存在、且本 MR 没有加重的 smell 当成这次变更的发现；只有它被新代码扩大或必须配合它才能工作时才纳入。

## 严重程度

严重程度衡量对未来理解和修改的实际影响，不是对个人风格的偏好：

- **P1 / blocking**：明确造成跨模块变更放大、关键行为未知、公共 interface 把大量复杂性推给所有调用者，或会使后续正确修改高度不可靠；应在合并前处理。
- **P2 / important**：局部但实质性地引入浅模块、信息泄漏、职责错位、投机性通用或不可验证的 interface；建议在本 MR 修复，或记录有约束的后续重构。
- **P3 / minor**：命名、文档、一致性或小范围显然性问题，修复成本低但能减少误用。
- **Question**：设计问题值得作者确认，但证据不足以称为缺陷；不要用它阻塞合并。

**Trade-off** 是非缺陷状态而不是优先级：复杂性是有意承担且有证据支撑的收益，单独记录，不要把它当成缺陷。P1/P2/P3 是给 Violation 或 Risk 的优先级；Question 和 Trade-off 使用自己的标签。常见组合是：`P1/P2/P3 + Violation`、`P1/P2/P3 + Risk`、`Question`、`Trade-off`。

组合不变量：`Violation` 或 `Risk` 必须且只能搭配 `P1`、`P2` 或 `P3`；`Question` 必须使用 `Question`；`Trade-off` 必须使用 `Trade-off`。不要生成例如 `P1 + Trade-off` 或 `P2 + Question` 的组合。

校准例子：把内部存储格式复制到两个会独立变化的层，通常至少是 P2；让所有调用者新增一组底层重试/格式参数，且没有统一 owner，可能是 P1；一个非显然的返回值缺少 interface 文档通常是 P3；仅仅“我能想到另一种写法”是 Question，而不是 P1/P2。

不要把“可以有另一个设计”自动标为 P1/P2。只有当替代设计明显降低本次可见的复杂性，并且当前设计有可追踪的未来代价时，才提高严重程度。

推荐结论的映射：`P1 + Violation` 或 `P2 + Violation` → `changes requested`；`P1 + Risk` 只有在合并前确实需要补齐证据或落实缓解措施时才可使用 `changes requested`，并明确它仍是 Risk；若本轮无法补证据，应降为较低优先级的 Risk 或 `Question`，使用 `approve with notes`。`P2/P3 + Risk`、`P3 + Violation`、`Question` 以及 `Trade-off` → `approve with notes`（除非仓库政策或用户明确要求阻塞）；没有设计发现 → `no design findings`。这只是设计轴结论，不代表其他审查轴通过。

## 输出格式

输出面向 MR 作者和 reviewer，优先给可定位、可行动的发现，不写泛泛的读书摘要：

```markdown
# Software design review

## Scope
- Diff: `<base>...<head>`
- Commits: `<命令结果或摘要>`
- Read: `<MR/spec/standards/ADR>`
- Verification: `<运行过的检查及结果>`

## Findings

### [<Severity>] 信息泄漏：<简短标题>
`path/to/file.ext:123`

**Severity**：P1 / P2 / P3 / Question / Trade-off。

**Observation**：指出 diff 做了什么，并给出必要的调用关系或接口事实。

**Why this matters**：说明它如何增加依赖、认知负荷、未知的未知或变更放大；给出一个具体未来变化。

**Suggested direction**：说明应把知识/责任收回哪个模块，或怎样缩小 interface；不要求未经证实的完整重写。

**Status**：Violation / Risk / Question / Trade-off。

**Confidence**：high / medium / low；附验证结果或待作者确认的问题。

**Alternatives considered**（对 public interface 或模块拆分必须填写）：方案 A 与方案 B；分别比较 interface 成本、通用性、实现收益，以及各自隐藏的责任。
```

标题中的 `<Severity>` 使用与组合不变量一致的标签：P1/P2/P3，或 `Question`、`Trade-off`。

规则：

- 一项发现只讨论一个根因；每项必须有文件、单行起点或精确 hunk、原则标签和建议方向。
- 先列 P1，再列 P2/P3，最后列 Question 和 Trade-off；不要把多个维度混成一个“总体感觉”。Trade-off 是独立的非缺陷记录，不参与 P1/P2/P3 排序。
- 只报告有证据支持的发现。若没有发现，明确写“未发现有证据支持的违反项”，并说明这不等于功能、安全或完整 spec 审查通过。
- 可选地在 findings 后添加 `## Trade-offs worth preserving`，只记录 MR 明确承担且合理的复杂性，避免把好的取舍误报成问题。
- 结尾用一行统计：`Findings: P1 x, P2 y, P3 z, Questions q, Trade-offs t.`，再给出 `Design-philosophy recommendation: changes requested / approve with notes / no design findings / unable to review`，遵循上面的映射。Risk、Question 和 Trade-off 要保留其状态，不得悄悄升级。
- 若无法锁定 diff（无可解析 base/head、ref 不一致或为空），只报告 Scope 限制和 `unable to review`，不要写“未发现违反项”或伪造统计。

## 完成标准

在结束前确认：

- [ ] 比较范围和 MR 版本已锁定，未混入工作树杂项；
- [ ] 已读到足以判断职责和调用关系的上下文；
- [ ] 每个 public interface 变化都检查了调用者需要知道的信息；
- [ ] 已按复杂性、模块深度、信息隐藏、一般性、错误/特殊情况、聚合/拆分、演化、文档、一致性和显然性逐项筛查；
- [ ] 每个报告项都有 diff 行号、原则、影响、建议和置信度；
- [ ] 每个报告项都分开填写 Status 和 Confidence；

- [ ] 已区分违反、风险和合理取舍；对已由 CI/工具明确验证通过的机械规则不重复报告，但仍检查其设计后果；
- [ ] 验证前后工作树状态可解释、没有把生成物或用户修改混入 diff；
- [ ] 已运行或明确说明相关验证，且没有把本 skill 当成功能、安全或完整 spec 审查。
