# 测试驱动开发

TDD 就是 red → green 循环。这个 skill 是让该循环产出值得保留的测试的参考：什么是好测试、测试应该放在哪里、有哪些反模式，以及循环的规则。每一轮循环都适用所有章节——应在循环开始前和进行中查阅，而不是结束后再看。

探索代码库时，读取 `CONTEXT.md`（如果存在），让测试名称和接口词汇符合项目的领域语言，并遵守所触及区域中的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变，测试不应随之失效。好测试读起来像规范——“用户可以用有效购物车完成结账”准确说明了存在什么能力——并且能经受重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝——测试放在哪里

**Seam** 是执行测试的公共边界：你无需伸入内部，就能在此接口上观察行为。测试只应位于 seams，绝不针对内部实现。

**只在预先约定的 seams 上测试。** 编写任何测试之前，先写下要测试的 seams，并与用户确认。不得在未经确认的 seam 上编写测试。你不可能测试所有东西——预先约定 seams，才能让测试工作落在关键路径和复杂逻辑上，而不是每个边缘情况上。

询问：“公共接口是什么？我们应该测试哪些 seams？”

如果该接口本身的形态仍未确定——模块应该多深、seam 应放在哪里、接口应该暴露什么——就调用 Skill tool 并传入 “codebase-design” 以获取相关词汇。它是 module、interface、depth、seam、adapter、leverage 和 locality 等术语的共同事实来源；它是供查阅的参考，而不是要运行的一次会话。

## 反模式

- **与实现耦合**——mock 内部协作者、测试私有方法，或通过旁路验证（例如绕过接口直接查询数据库）。识别信号：重构后行为没有变化，测试却失败了。
- **同义反复**——断言用与代码相同的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`、以同样方法手工推导的 snapshot、断言某个常量等于其自身），因此它在构造上必然通过，永远无法与代码产生分歧。预期值必须来自独立的事实来源——已知正确的字面值、完整推演过的示例或规范。
- **水平切片**——先写完所有测试，再写所有实现。批量测试验证的是_想象中_的行为：测试的是事物的_形状_而非用户可见行为，测试对真实变更变得不敏感，并且会在理解实现前就把测试结构定死。应改为使用**垂直切片**——一个测试 → 一个实现 → 重复；每个测试都是一枚 **tracer bullet**，会响应上一轮循环带来的认知。

## 循环规则

- **先 red，再 green。** 先写失败的测试，然后只写足以让它通过的代码。不要预判未来的测试，也不要添加推测性的功能。
- **一次一个切片。** 每轮只处理一个 seam、一个测试和一个最小实现。
- **重构不属于这个循环。** 重构应在 review 阶段进行（参见 `code-review` skill），而不在 red → green 实现循环中进行。
