# 原型

原型是**用来回答一个问题的一次性代码**。问题决定它的形态。

## 选择分支

从用户的提示、周边代码中判断要回答哪个问题；如果用户在线，也可以直接询问：

- **“这套逻辑 / 状态模型合理吗？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的单 HTML 文件，其中包含自由操作按钮和带标签页的引导式演练，让状态机跑过那些仅靠纸面难以推理的情况，并让非开发者也能操作。
- **“它应该是什么样？”** → [UI.md](UI.md)。在同一路由上生成几种截然不同的 UI 方案，可通过 URL 查询参数和悬浮底栏切换。

两个分支会产出截然不同的工件；选错分支会让整个原型白做。如果问题确实有歧义且联系不上用户，就默认选择更符合周边代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这个假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性的，并明确标注。** 把原型代码放在接近其实际使用位置的地方（紧邻它所针对的模块或页面），让上下文一目了然；但命名必须让随手阅读代码的人看出这是原型而非生产代码。对于一次性的 UI 路由，遵循项目已有的路由约定，不要发明新的顶层结构。
2. **启动极其简单。** UI 原型只需运行项目任务执行器中的一个命令即可启动，例如 `pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是一个用户双击即可打开的 HTML 文件。无论哪种，都不应让用户思考如何启动。
3. **默认不持久化。** 状态保存在内存中。持久化是原型要_验证_的对象，而不是原型自身的依赖。如果问题明确涉及数据库，就使用临时数据库或名称中明确带有 “PROTOTYPE — wipe me” 的本地文件。
4. **跳过打磨。** 不写测试；除保证原型_可运行_所必需的处理外，不做错误处理；不做抽象。目标是快速学到东西。
5. **把状态展示出来。** 每次操作后（逻辑分支）或每次切换方案时（UI 分支），打印或渲染完整的相关状态，让用户看到发生了什么变化。
6. **完成后留存。** 把验证过的决策合入真实代码，然后将原型本身作为**一手资料**留存：提交到主分支之外的一次性分支，并在实现 issue 上留下指向该分支的上下文指针。答案也要留存——包括结论以及它解决的问题——写入 issue 或 commit。主分支只保留经过验证的决策。
