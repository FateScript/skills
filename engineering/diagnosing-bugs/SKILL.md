# 诊断缺陷

一套处理困难 bug 的严格方法。只有在明确说明理由时才能跳过阶段。

探索代码库时，读取 `CONTEXT.md`（如果存在），以建立对相关 module 的清晰心智模型；同时检查所涉及区域中的 ADR。

## 脱敏

这项技能要求你展示命令、输出和捕获的产物。**必须先对每一项 secret 脱敏**——用 `<REDACTED>` 替换它。围绕环境变量构建循环，使凭据留在环境中，而不会出现在展示内容里。捕获的产物含有认证 header：只引用真正承载有效信号的行。

如果脱敏后的输出不足以诊断 bug，请明确说明并询问用户。

## 阶段 1——建立反馈循环

**这就是这项技能的核心。** 其他一切都只是机械步骤。如果你拥有一个针对该 bug 的**紧凑**通过/失败信号——一个会在_这个_ bug 上变红的信号——你就能找到原因；二分、假设检验和插桩都只是在使用这个信号。如果没有这样的信号，再怎么盯着代码也无济于事。

在这里投入远超其他阶段的精力。**大胆尝试。发挥创造力。绝不放弃。**

### 构造反馈循环的方法——大致按以下顺序尝试

1. 在能够触达该 bug 的 seam 上编写**失败测试**——unit、integration 或 e2e。
2. 针对正在运行的开发服务器编写 **Curl / HTTP 脚本**。
3. 使用夹具输入执行 **CLI 调用**，将 stdout 与已知正确的快照进行 diff。
4. 编写**无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，并对 DOM/console/network 作出断言。
5. **重放捕获的 trace。** 将真实的网络请求、payload 或事件日志保存到磁盘；在隔离环境中通过相应代码路径重放它。
6. **一次性 harness。** 启动系统的最小子集（一个 service、mock 后的依赖），通过一次函数调用执行包含 bug 的代码路径。
7. **Property / fuzz 循环。** 如果 bug 是“有时输出错误”，就运行 1000 个随机输入并寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、dataset、version），就自动执行“在状态 X 启动、检查、重复”，以便使用 `git bisect run`。
9. **差分循环。** 让同一输入分别通过旧版本与新版本（或两种 config），再对输出进行 diff。
10. **HITL bash 脚本。** 最后的手段。如果必须由人点击，就用 `scripts/hitl-loop.template.sh` 来引导_他们_操作，使循环仍然结构化。捕获的输出再反馈给你。

建立正确的反馈循环以后，bug 就已经解决了 90%。

### 收紧循环

把循环当作产品来对待。一旦有了_一个_循环，就要**收紧**它：

- 能否让它更快？（缓存准备工作、跳过无关初始化、缩小测试范围。）
- 能否让信号更精确？（针对具体症状断言，而不是只检查“没有崩溃”。）
- 能否让结果更确定？（固定时间、设置 RNG seed、隔离文件系统、冻结网络。）

一个耗时 30 秒且不稳定的循环，只比没有循环略好；一个耗时 2 秒且结果确定的循环才足够紧凑——它是调试的超级能力。

### 非确定性缺陷

目标不是得到一次干净的复现，而是获得**更高的复现率**。将触发过程循环 100 次、并行执行、施加压力、缩小时间窗口、注入 sleep。复现率为 50% 的 flaky bug 可以调试；1% 则不行——持续提高复现率，直到可以据此调试。

### 确实无法建立循环时

停下来并明确说明情况。列出已经尝试过的方法。向用户请求以下任意一项：(a) 能够复现问题的环境访问权限，(b) 已脱敏的捕获产物（HAR 文件、日志 dump、core dump、带时间戳的屏幕录像），或 (c) 添加临时生产环境插桩的许可。**不要**在没有循环的情况下继续提出假设。

### 完成标准——一个紧凑且能变红的循环

当循环既**紧凑**又**能变红**时，阶段 1 才算完成：你能给出**一条命令**——脚本路径、测试调用或 curl——并且已经**至少运行过一次**（展示调用及其已脱敏的输出），同时满足：

- [ ] **能变红**——它执行真实的 bug 代码路径，并对**用户所说的确切症状**作出断言，因此能在这个 bug 上变红，并在修复后变绿。不能只是“运行时没有报错”——它必须能_捕获这个特定 bug_。
- [ ] **结果确定**——每次运行都给出相同结论（对于 flaky bug：按照上文方法固定一个较高的复现率）。
- [ ] **快速**——耗时以秒计，而不是分钟。
- [ ] **Agent 可独立运行**——你可以在无人值守的情况下执行它；只有通过 `scripts/hitl-loop.template.sh` 才允许将人纳入循环。

如果你发现自己在这条命令出现之前就在阅读代码、构建理论，**立即停下——直接跳到假设，正是这项技能要防止的错误。** 没有能变红的命令，就不能进入阶段 2。

## 阶段 2——复现并最小化

运行这个循环。看着它变红——bug 出现了。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是恰好出现在附近的另一种失败。找错 bug 就会得到错误修复。
- [ ] 失败在多次运行中都可复现（对于非确定性 bug，复现率应足够高，可以据此调试）。
- [ ] 你已经捕获确切症状（错误消息、错误输出或缓慢的耗时），以便后续阶段验证修复是否真正解决了问题。

### 最小化

一旦循环变红，就将复现场景缩减到**仍然会变红的最小场景**。每次只删减一项输入、调用方、config、数据或步骤，并在每次删减后重新运行循环——只保留对失败起关键作用的元素。

为什么值得这样做：最小复现会缩小阶段 3 的假设空间（剩下的可疑活动部件更少），并在阶段 5 中成为干净的回归测试。

当**所有剩余元素都不可或缺**时才算完成——移除任何一个都会使循环变绿。

在完成复现_并且_最小化之前，不要继续。

## 阶段 3——提出假设

在检验任何假设之前，先生成 **3–5 个按可能性排序的假设**。只提出一个假设会让你锚定在第一个看似合理的想法上。

每个假设都必须**可证伪**：明确写出它会作出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更加严重。”

如果无法陈述预测，这个假设就只是一种感觉——将其丢弃或进一步明确。

**在检验之前向用户展示排序后的列表。** 用户通常掌握能立即改变排序的领域知识（“我们刚刚部署了与第 3 项有关的变更”），或者知道哪些假设早已被排除。这是一个成本很低、却能节省大量时间的检查点。不要停在这里等待——如果用户暂时不在线，就按照你的排序继续。

## 阶段 4——插桩

每一个探针都必须对应阶段 3 中的一项具体预测。**一次只改变一个变量。**

工具偏好：

1. 如果环境支持，优先使用 **Debugger / REPL 检查**。一个 breakpoint 胜过十条日志。
2. 在能够区分不同假设的位置添加**有针对性的日志**。
3. 绝不要“记录一切，然后 grep”。

**为每条 debug 日志添加唯一前缀**，例如 `[DEBUG-a4f2]`。这样结束时只需 grep 一次就能完成清理。没有标签的日志会留下；有标签的日志必须删除。

**性能分支。** 对于性能回归，日志通常不是正确手段。应该先建立基线测量（计时 harness、`performance.now()`、profiler、query plan），然后进行二分。先测量，再修复。

## 阶段 5——修复并添加回归测试

在修复之前**先编写回归测试**——但前提是存在一个**正确的 seam**。

正确的 seam 应当让测试按照 bug 在调用点真实发生的方式，执行**真实的 bug 模式**。如果唯一可用的 seam 太浅（bug 需要多个调用方，却只能做单调用方测试；或 unit test 无法复现触发 bug 的调用链），那么在该处编写的回归测试只会带来虚假的信心。

**如果不存在正确的 seam，这本身就是诊断结果。** 将其记录下来。代码库架构正在阻碍你彻底锁定这个 bug。把这一点标记给下一阶段。

如果存在正确的 seam：

1. 将最小复现转换为该 seam 上的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始的（未经最小化的）场景，重新运行阶段 1 的反馈循环。

## 阶段 6——清理

在宣布完成之前，必须确认：

- [ ] 原始复现不再出现（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录不存在合适的 seam）
- [ ] 所有 `[DEBUG-...]` 插桩均已移除（`grep` 该前缀）
- [ ] 一次性 prototype 已删除（或移至明确标注的 debug 位置）
- [ ] 最终被证实正确的假设已写入 commit / PR message——让下一位调试者能够从中学习
