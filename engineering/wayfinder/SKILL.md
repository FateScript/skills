一个松散的想法出现了——它太大，单个 agent 会话无法容纳；它还被迷雾包围：从这里通往**目的地**的道路尚不可见。Wayfinding 的重点是找到这条路，而不是一头冲向目的地。这个 skill 会在仓库的 issue tracker 上把路线绘制成一张**共享地图**，然后逐一处理其中的**决策 tickets**——每张 ticket 所解决的是一个决策问题，而不是要执行的构建切片——直到路线清晰。

每项工作的目的地都不同，而为它命名就是绘图的第一个动作——它会塑造每一张 ticket。目的地可能是一份要交接并持续迭代的 spec、一个要在规划开始前锁定的决策，也可能是一项直接落地的改动，例如数据结构迁移。地图不限定领域——工程工作、课程内容，任何符合这种形态的工作都可以。

## 只规划，不执行

Wayfinder 默认用于**规划**：每张 ticket 解决一项决策；当道路已经清晰——即在有人着手做事前，没有任何待定决策——地图就完成了。想直接动手执行的冲动，通常说明你已经走到地图边缘，该交接了。某项工作可以在其**备注**中覆盖这个默认规则，把执行本身纳入地图；除此之外，应产出决策，而不是交付物。

## 按名称引用

每张地图和 ticket 都是一条 issue，因此都有一个**名称**——也就是其标题。在人类会阅读的一切内容中——叙述、地图的 Decisions-so-far——都应按名称引用它，绝不要只写裸 id、编号或 slug。一堵由 `#42, #43, #44` 组成的墙无法阅读；名称让人一眼就能理解。id 和 URL 并不会消失——名称包裹着它的链接——但它们位于名称_内部_，绝不能代替名称本身。

## 地图

地图是本仓库 issue tracker 上的一条 issue，带有 `wayfinder:map` label——它是规范工件。地图中的 tickets 是它的 child issues。

地图是**索引**，不是存储库。它列出已做出的决策，并指向保存详情的 tickets；每项决策只存在于一个地方——它的 ticket——因此地图绝不复述，只概括并链接。

**地图、child tickets、blocking 和 frontier queries 实际存放和表达在哪里，取决于 tracker。** issue tracker 应已提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。查阅 tracker 文档的 “Wayfinding operations” 小节，了解_本_仓库如何表达这些操作。如果没有提供 tracker，默认使用本地 Markdown tracker。

### 任务票

每张 ticket 都是地图的一条 **child issue**；tracker 的 issue id 就是它的身份标识。正文是一个问题，规模应适合一次 100K token 的 agent 会话：

```markdown
## 问题

<此 ticket 要解决的决策或调查>
```

每张 ticket 都带有一个 `wayfinder:<type>` label——`research`、`prototype`、`grilling`、`task` 之一（参见[任务票类型](#任务票类型)）。

会话在开展任何工作前，**首先**把 ticket 指派给推动地图的 dev，以此**认领**它，让并发会话跳过。这个 assignee _就是_认领标记：开放且无人指派的 ticket 就是未认领 ticket。

Blocking 使用 tracker 的**原生**依赖关系——这至关重要，因为它会在 tracker 自己的 UI 中_直观_渲染前沿，让人类无需打开地图就能看出哪些任务可接手。只有不支持原生 blocking 的 tracker 才退回到正文约定。当阻塞某张 ticket 的所有 tickets 都已关闭时，该 ticket 就是**未阻塞**的；**前沿**则是开放、未阻塞且未认领的 child issues——也就是已知世界的边缘。

答案不属于正文——它会在解决时记录（参见[沿地图推进](#沿地图推进)）。解决 ticket 期间创建的资源应从 issue 链接，而不是粘贴到其中。

## 任务票类型

每张 ticket 要么是 **HITL**——人在回路中，与能代表自己发言的人类_共同_处理；要么是 **AFK**，由 agent 独立推动。HITL ticket 只能通过这种实时交流解决；agent 绝不能代替人类回答属于人类一方的问题（一个自问自答的 grilling agent 已经破坏了这个流程）。

- **研究**（AFK）：阅读文档、第三方 API 或知识库等本地资源，找出某项决策正在等待的事实。由 subagent 调用 Skill tool 并传入 “research” 来解决。当需要当前工作目录之外的知识时使用。
- **原型**（HITL）：制作一个便宜、粗糙、具体且可供反馈的工件，提高讨论的保真度——例如提纲、粗略方案、stub 或 UI/logic code；通过调用 Skill tool 并传入 “prototype” 完成。把 prototype 作为 asset 链接。当关键问题是“它应该看起来怎样”或“它应该如何表现”时使用。
- **追问**（HITL）：对话。默认类型。始终调用 Skill tool 两次，分别传入 “grilling” 和 “domain-modeling”。
- **任务**（HITL 或 AFK）：在做出某项_决策_前必须完成的手工工作——没有需要决定、制作原型或研究的内容，但在工作完成前讨论会被阻塞。例如注册服务以便评估其 API、配置访问权限、移动数据以观察其形态。这是唯一会_执行_而不是做决策的类型——它之所以能进入地图，是因为它会解除一项决策的阻塞，而不是因为它交付了目的地。如果 agent 可以独立推动，就以 AFK 方式完成；否则给人类一份精确的 checklist（HITL）。工作完成时即为解决；答案应记录完成了什么，以及后续 tickets 所依赖的任何事实（credentials location、new URLs、row counts）。

## 战争迷雾

地图是_刻意_不完整的：不要绘制目前还看不清的内容。开放 tickets 之外是**战争迷雾**——你能模糊看见即将出现的决策和调查，却还无法把它们精确钉住，因为它们依赖尚未解决的问题。解决一张 ticket 会驱散前方的迷雾，将现在已经能明确描述的内容逐一转化成新 tickets，直到通往目的地的道路清晰，且没有剩余 tickets。

地图的**尚未明确**小节用于记录这种模糊视野：疑似存在的问题、稍后要重新查看的区域。这是_朝向_目的地的未知前沿——其中一切都在范围内，只是还不够清晰，无法成为 ticket。根据当前视野，写得粗略或完整都可以；对于想了解工作将走向何方的协作者，它也充当路标。

**迷雾还是 ticket？** 判断标准是你现在能否精确陈述问题——_不是_你现在能否回答它。

- **创建 ticket 的条件**：问题已经足够清晰——即使它当前被阻塞、还无法处理。
- **放入“尚未明确”的条件**：你还无法如此清晰地描述问题。不要提前把迷雾切成 ticket 大小的块：它比 ticket 更粗糙；当前沿抵达时，一块迷雾可能转化为多张 tickets，也可能一张都不会产生。

**尚未明确**不包含已经决定的内容（到目前为止的决策）、已经存在的开放 ticket，以及范围之外的内容（见下一节）。

## 范围之外

迷雾只会聚集在_通往_目的地的方向。目的地确定了范围，因此超出目的地的工作属于**范围之外**——它不是迷雾，也不应放入**尚未明确**。地图上有专门的**范围之外**小节：记录你有意识地从_本次_工作中排除的事项。是否放在这里取决于范围，而不是清晰度。

范围之外的工作永远不会转化——前沿止步于目的地——因此只有重新划定目的地时，它才会再次出现；而且应作为一项全新的工作，不是恢复旧工作。

判定某件事在范围之外是一项范围界定行为，不是路线上的一步。当已经存在的 ticket 原来位于目的地之外——可能绘图时错误纳入，也可能由某项解决结果揭示——应**关闭它**（已关闭 ticket 明确不属于前沿），并在**范围之外**小节留下一行：概述内容及其超出范围的原因，并链接已关闭 ticket。不要把它放入**到目前为止的决策**；后者记录实际走过的路线，而范围边界并不是路线上的一步。

## 调用方式

有两种模式。无论哪种，**每个会话都绝不要解决超过一张 ticket**——research tickets 除外。

### 绘制地图

用户带着一个松散想法调用。

1. **命名目的地。** 调用 Skill tool 两次，分别传入 “grilling” 和 “domain-modeling”，明确这张地图要寻找通往什么的路线——spec、decision 或 change。目的地决定范围，因此必须先确定。
2. **绘制前沿。** 再次追问，这次采用**广度优先**：向整个空间铺开，而不是深入任何单一线索，找出开放决策以及现在就能采取的第一步。**如果这一步没有发现迷雾**——通往目的地的道路已经清晰，整个旅程小到一次会话即可完成——就不需要地图。停止，并询问用户想如何继续。
3. **创建地图**（label 为 `wayfinder:map`）：填好目的地和备注，到目前为止的决策保持为空，并把迷雾勾勒在**尚未明确**中。
4. **把目前能够明确描述的内容创建成 tickets**，作为地图的 child issues——然后在**第二轮**连好 blocking edges（issues 必须先有 ids，才能互相引用）。连边会把它们分入前沿和被阻塞集合；所有尚无法明确描述的内容都留在迷雾中——也就是**尚未明确**小节。
5. **启动 research subagents。** 对刚刚创建的每一张 `research` ticket，启动一个 subagent，让它调用 Skill tool 并传入 “research”，并行解决该 ticket；将研究结果捕获到一次性的 `research/<name>` branch，并从 ticket 留下 context pointer。
6. 停止——绘图就是一个会话的工作；它本身不手动解决任何 ticket。

### 沿地图推进

用户提供一张地图（URL 或编号）来调用。指定 ticket 是**可选的**——如果用户没有指定，就由你而非用户选择下一个决策。

1. 加载**地图**——低分辨率视图，而不是每张 ticket 的完整正文。
2. 选择 ticket。如果用户点名了某张，就使用它；否则按顺序选择第一张前沿 ticket。**认领它**：开始任何工作前，先把它指派给自己。
3. 解决它——**按需放大**：需要时获取任何相关或已关闭 ticket 的完整正文；调用 `## 备注` 区块中点名的 skills 对应的 Skill 工具。如果不确定，就调用 Skill 工具两次，分别传入 “grilling” 和 “domain-modeling”。
4. 记录解决结果：将答案发布为一条**解决评论**，**关闭** issue，并向地图的“到目前为止的决策”追加一条 context pointer。
5. 添加新浮现的 tickets（先创建，后连边）；将答案已使其变得可明确描述的迷雾转化为 tickets，并从**尚未明确**中移除每一块已转化的迷雾，让它只存在于新 ticket 中。如果答案揭示某张 ticket——当前这张或其他 ticket——位于目的地之外，就将其**判定为范围之外**，而不是作为路线上的一步解决。如果该决策使地图其他部分失效，更新或删除相应 tickets。

用户可能会并行处理多张未阻塞 tickets，因此应预期其他会话会同时编辑 tracker。
