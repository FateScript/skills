# 领域建模

在设计过程中，主动构建并打磨项目的领域模型。这是一项_主动_实践——质疑术语、构造边界情况场景，并在术语表和决策一旦明确时立即将其写下。（仅仅为了了解词汇而_读取_ `CONTEXT.md` 并不属于这项技能——那只是任何技能都能遵循的一行习惯。这项技能适用于你正在改变模型，而不只是使用它的时候。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则该仓库包含多个上下文。该映射会指出每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件——只有确实有内容要写时才创建。如果 `CONTEXT.md` 不存在，就在第一个术语得到明确时创建它。如果 `docs/adr/` 不存在，就在需要第一份 ADR 时创建该目录。

## 会话期间

### 对照术语表质疑用词

当用户使用的术语与 `CONTEXT.md` 中已有的语言冲突时，立即指出：“你的术语表将 ‘cancellation’ 定义为 X，但你现在似乎指的是 Y——究竟是哪一个？”

### 明确模糊语言

当用户使用模糊或一词多义的术语时，提出一个精确的规范术语：“你说的是 ‘account’——你指的是 Customer 还是 User？它们是不同的概念。”

### 讨论具体场景

讨论领域关系时，用具体场景对其进行压力测试。构造能够探查边界情况的场景，迫使用户精确说明概念之间的界限。

### 与代码交叉核对

当用户说明某项机制如何运作时，检查代码是否与之相符。如果发现矛盾，要明确指出：“你的代码会取消整个 Order，但你刚才说可以部分取消——哪一种才是正确的？”

### 就地更新 CONTEXT.md

术语一旦明确，就当场更新 `CONTEXT.md`。不要攒到最后统一处理——要在结论出现时立即记录。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应完全不含实现细节。不要把 `CONTEXT.md` 当作 spec、草稿本或存放实现决策的地方。它仅仅是一份术语表。

### 谨慎提议 ADR

只有在以下三个条件全部满足时，才提议创建 ADR：

1. **难以逆转**——日后改变决定的成本不可忽略
2. **缺少上下文就会令人困惑**——未来的读者会问：“为什么要这样做？”
3. **源自真正的权衡**——确实存在其他可选方案，而你出于具体原因选择了其中一个

只要任意一项不满足，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
