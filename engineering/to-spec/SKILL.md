这个 skill 会根据当前对话上下文和对代码库的理解产出一份 spec。**不要**访谈用户——只综合你已经知道的内容。

issue tracker 和 triage label 词汇应已提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果还没有探索仓库，先探索以理解代码库的当前状态。在整份 spec 中使用项目领域术语表的词汇，并遵守所触及区域中的任何 ADR。

2. 勾勒准备在哪些 seams 上测试该功能。应优先使用已有 seam，而不是创建新 seam。使用尽可能高层的 seam。如果确实需要新 seam，就在能够做到的最高层提出。代码库中的 seams 越少越好——理想数量是一个。

与用户确认这些 seams 是否符合他们的预期。

3. 使用下面的模板编写 spec，然后发布到项目 issue tracker。应用 `ready-for-agent` triage label——无需额外 triage。

<spec-template>

## 问题陈述

从用户视角描述用户面临的问题。

## 解决方案

从用户视角描述问题的解决方案。

## 用户故事

一份**很长的**编号用户故事列表。每个用户故事都应采用以下格式：

1. 作为 <actor>，我想要 <feature>，从而获得 <benefit>

<user-story-example>
1. 作为一名手机银行客户，我想查看账户余额，从而能对自己的支出做出信息更充分的决定
</user-story-example>

这份用户故事列表应极其详尽，并覆盖该功能的所有方面。

## 实现决策

已经做出的实现决策列表。可以包括：

- 将构建/修改的模块
- 将修改的模块接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不要**包含具体文件路径或代码片段。它们可能很快过时。

例外：如果 prototype 产出的某个片段比文字更精确地编码了一项决策（状态机、reducer、schema、type shape），可以把它内联到相关决策中，并简短注明它来自 prototype。只保留富含决策的部分——不是可运行的 demo，只保留重要内容。

## 测试决策

已经做出的测试决策列表。包括：

- 对好测试的描述（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中相似类型的测试）

## 范围之外

描述此 spec 范围之外的事项。

## 补充说明

关于该功能的任何补充说明。

</spec-template>
